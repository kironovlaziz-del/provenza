# Self-hosting Provenza

Provenza runs on your own server, so your prompts, policies, audit records and
keys never leave it. This guide takes you from a fresh server to a running
control plane, and covers keeping it running and up to date.

## Requirements

| | |
|---|---|
| Server | Linux with systemd: **Ubuntu 24.04+**, Debian 13+, RHEL/Rocky/Alma 9.3+ or Fedora; 2 vCPU, **4 GB RAM**, 20 GB disk |
| Software | **Podman 4.4+** with `netavark` and `aardvark-dns`, `git`, `openssl`. The installer installs whatever is missing from the distribution's packages. |
| Access | root (`sudo`): the stack is rootful Podman containers managed by systemd |
| Network | A domain name whose DNS record points at the server; ports **80 and 443** open to the internet |

Provenza's services are systemd units generated by Podman's Quadlet from the
templates in `deploy/quadlet/`. Ubuntu 22.04 and Debian 12 ship a Podman too
old for Quadlet (3.4 and 4.3); upgrade the OS first.

## Install

```bash
git clone https://github.com/kironovlaziz-del/provenza.git /opt/provenza
cd /opt/provenza
sudo ./install.sh
```

The installer asks for:

- the domain;
- the organization name;
- the first administrator's e-mail, name and password (12 characters or more).

It then does everything else, and a few minutes later prints the address to
sign in at:

```
→ Checking this server
  ✓ Podman 4.9.3 (Quadlet, netavark)
  ✓ 7951 MB RAM
  ✓ 61 GB free disk
→ Configuration
  ✓ secrets generated into deploy/.env (mode 600)
  ✓ app.company.com resolves to 203.0.113.10
→ Building the images (the first build takes a few minutes)
  ✓ images ready: localhost/provenza/backend:local, localhost/provenza/web:local
→ Installing the systemd units
    ✓ 23 Quadlet units in /etc/containers/systemd, provenza.target enabled
→ Starting the stack
  ✓ migrations applied; API, workers, web UI and HTTPS proxy are up
→ Creating the administrator
  ✓ daily backup scheduled (systemctl list-timers provenza-backup.timer)

✓ Provenza is running at https://app.company.com
```

**Without cloning first.** Read the script before piping it into a shell:

```bash
curl -fsSL https://raw.githubusercontent.com/kironovlaziz-del/provenza/main/install.sh | sudo bash
```

It clones the repository into `/opt/provenza`, or the directory given with
`--dir`, and continues from there.

**Unattended.** For example from cloud-init or Ansible:

```bash
sudo PROVENZA_ADMIN_PASSWORD='…' ./install.sh --yes \
  --domain app.company.com --org "Company" --admin-email admin@company.com
```

| Option | |
|---|---|
| `--admin-name NAME` | The administrator's display name. |
| `--no-backup` | Do not schedule the daily backup (`--no-cron` still works). |
| `--force` | Go on despite host warnings: low memory or disk, ports 80/443 already in use. |
| `PROVENZA_READY_TIMEOUT` | Seconds to wait for the stack to become healthy (default 900). |

**Trying it on your own machine.** Use `localhost` as the domain. Caddy then
issues a local certificate, and the browser warns about it once.

### What the installer does

1. **Checks the host:** systemd, Podman 4.4+ with Quadlet and the netavark network backend (and installs them if missing), memory, disk, whether the domain resolves, and whether ports 80/443 are free. If Provenza is still running on Docker here, it stops and points to the migration below.
2. **Writes `deploy/.env`** (mode 600) with freshly generated secrets:
   - `SECRET_KEY` for signing sessions;
   - `ENCRYPTION_KEY` for stored API keys and secrets;
   - the PostgreSQL and Redis passwords.

   There are no default passwords anywhere: the backend refuses to start with a missing or well-known secret.
3. **Builds the images** with Podman and pulls PostgreSQL 16, Redis 7, Caddy, Prometheus, Grafana and Alertmanager.
4. **Installs the systemd units** (`deploy/scripts/units.sh install`): the Quadlet templates are filled in with the values from `deploy/.env` and written to `/etc/containers/systemd`. Every container becomes a service (`provenza-postgres`, `provenza-backend`, …), all of them part of `provenza.target`, which starts at boot. Migrations run in their own one-shot service before anything that needs the database.
5. **Starts the stack and waits** until every service reports healthy.
6. **Creates the organization and its first administrator.** The password reaches the container through the environment and never appears in a command line.
7. **Schedules a daily backup** at 03:15 with the systemd timer `provenza-backup.timer`.

Running `sudo ./install.sh` again is safe: it keeps the existing `deploy/.env`,
rebuilds the images, re-renders the units and leaves existing users alone.

### Moving an existing Docker installation to Podman

Installations made before the switch run on Docker compose. Move one, data
included:

```bash
cd /opt/provenza && git pull
sudo ./deploy/scripts/migrate-from-docker.sh
```

1. While Docker keeps serving, it builds the images, pulls the others and installs the units.
2. It stops the application and takes a `pg_dump` into `deploy/backups/` (a safety copy).
3. It stops the Docker containers and disables their restart, without deleting them, then copies each Docker volume into the Podman volume of the same name (`provenza_pg-data`, `provenza_caddy-data`, …). The TLS certificates move along with the rest, so nothing is re-issued.
4. It starts `provenza.target` and waits until every service is healthy.
5. If something does not come up, it stops the Podman services and starts the Docker containers again. The Docker volumes are never modified.

The downtime is a few minutes. The old cron line for `backup.sh` is replaced by
`provenza-backup.timer`. Keep the Docker containers and volumes for a while: the
script prints the commands to go back and, later, to delete them.

### First steps after installing

1. **Back up `deploy/.env`** to somewhere off the server, such as a password manager. Without its `ENCRYPTION_KEY`, no backup can be read.
2. Sign in and follow the **setup checklist** on the dashboard:
   - connect an AI provider;
   - activate a policy;
   - register the first agent;
   - set up notifications;
   - require two-factor sign-in.
3. Under **My profile**, turn on two-factor sign-in for yourself. Then, under **Settings → Users**, require it for admins and approvers.
4. Connect an agent:
   - **Agents** → create an enrollment token;
   - on the agent's host, install the SDK: `pip install provenza` (or the JS or Go SDK).

## HTTPS

Caddy obtains and renews a Let's Encrypt certificate for the domain by itself.
It needs two things:

- the domain's DNS record pointing at the server;
- ports 80 and 443 reachable from the internet. Let's Encrypt validates over port 80.

No e-mail address is required. Let's Encrypt no longer sends expiry
reminders, and Caddy renews certificates well before they expire.

Caddy also sets HSTS and the other security headers, and the application sends
its own as well.

**Another web server already on 80/443.** The installer warns about this.
Either stop the other server, or put Provenza behind it:

1. Set `HTTP_PORT` and `HTTPS_PORT` in `deploy/.env` to free ports.
2. Proxy your domain to Caddy's HTTPS port.

## Backups

The installer schedules `deploy/scripts/backup.sh` daily with the systemd timer
`provenza-backup.timer` (`systemctl list-timers provenza-backup.timer`; logs:
`journalctl -u provenza-backup`). Each backup is a
`pg_dump` of the database plus the uploaded files, stored in `deploy/backups/`
and kept for 14 days (`BACKUP_KEEP_DAYS`).

To run one by hand:

```bash
cd /opt/provenza/deploy && sudo ./scripts/backup.sh
```

Copy `deploy/backups/` off the server regularly. A backup that stays on the
same disk does not survive the loss of that disk.

To restore (this replaces all current data, after asking you to confirm):

```bash
cd /opt/provenza/deploy
sudo ./scripts/restore.sh backups/provenza-20261012-031500.dump
```

`deploy/.env` must hold the `ENCRYPTION_KEY` that was in use when the backup
was made.

## Upgrade

```bash
cd /opt/provenza
sudo ./upgrade.sh                    # the latest version of the branch you installed
sudo ./upgrade.sh --version v1.4.0   # or a specific release
```

The script:

1. **Shows what is new and asks for confirmation.**
2. **Builds the new images** while the current version keeps serving.
3. **Stops outside access, then makes a backup.** Nothing can change data during the backup. This is the only downtime, usually under a minute.
4. **Starts the new version.** Its database migrations run first.
5. **Rolls back if anything is not healthy:** it restores the previous code, units and images, and, if the migrations had already changed the database, the database from the backup taken in step 3.

The previous images are kept as `:rollback` until the next upgrade.

Options:

- `--yes` skips the question;
- `--force` upgrades over local changes to tracked files. Without it, the script stops and lists them, so a local fix is never silently overwritten.

## Operating

The installer puts the `provenza` command in `/usr/local/bin`; it asks for
`sudo` by itself.

| Task | Command |
|---|---|
| Status: services, containers, health checks, next backup | `provenza status` |
| Logs | `provenza logs backend` (any service; `-f` follows, `-n 500` for more), `provenza logs` for all |
| Start / stop / restart | `provenza start` · `provenza stop` · `provenza restart` |
| One service | `provenza restart caddy` |
| Upgrade | `provenza upgrade` (see Upgrade above; with no new code it refreshes the PostgreSQL, Redis, Caddy and monitoring images) |
| Rebuild the code on disk | `provenza rebuild` - after a manual `git pull` or a patch, which `upgrade` would not see: build, back up, restart; no fetch and no rollback |
| Backup now | `provenza backup` |
| Another administrator | `provenza run create-admin --org "Company" --email someone@company.com` |
| A shell in a container | `sudo podman exec -it backend sh` |
| Health from the UI | **Settings → System status** |

Services: `postgres`, `redis`, `migrate`, `backend`, `worker`, `beat`,
`frontend`, `caddy`, `prometheus`, `grafana`, `alertmanager`. Each is the
systemd unit `provenza-<service>`, so `systemctl` and `journalctl -u` work too.
Grafana (`127.0.0.1:3001`) and Prometheus (`127.0.0.1:9090`) listen on the
server only: reach them through an SSH tunnel,
`ssh -L 3001:127.0.0.1:3001 user@server`.

Do not share the output of `podman inspect` or the files in `deploy/.runtime/`:
they contain the secrets from `deploy/.env`.

Every setting is documented in `deploy/.env.example`. The most common:

- `API_WORKERS`, `CELERY_CONCURRENCY`: capacity;
- `SMTP_*`: e-mail notifications;
- `OUTBOUND_PRIVATE_ALLOWLIST`: internal hosts Provenza may call, such as an in-house Vault or model server;
- `*_MEMORY`: container memory limits.

After editing `deploy/.env`, run `provenza units && provenza restart`.
The domain, ports, memory limits and passwords are written into the units, so
`units.sh install` is needed for them; other settings only need the restart.

## Keeping prompts on your own network

To make sure no prompt reaches a cloud AI service, an administrator sets
**Connections → AI provider policy → Self-hosted only**. Provenza then:

- connects only to non-public addresses for every provider call (the
  playground, the LLM gateway, the request queue), checked at each
  connection after the name is resolved, so a base URL or a DNS record
  cannot lead to the internet;
- refuses connections without a base URL (the vendor's cloud API) before
  anything is sent;
- refuses agents' direct calls to known cloud AI services.

Your model server (for example vLLM or Ollama) must be reachable from the
server and listed in `OUTBOUND_PRIVATE_ALLOWLIST`, e.g.
`OUTBOUND_PRIVATE_ALLOWLIST=llm.corp.local,10.20.0.0/16`. Connect it as an
OpenAI-compatible connection with its base URL, such as
`http://llm.corp.local:8000/v1`.

## Locking agents down

Network rules that leave agents only the egress proxy, and a check that they
hold: [egress-lockdown.md](egress-lockdown.md). The bundled Caddy already
routes the check's beacon (`/egress-beacon/`) to the backend.

## Troubleshooting

| Symptom | What to do |
|---|---|
| The site works on the server (`provenza status` ✓) but times out from anywhere else | Something sets the firewall's FORWARD policy to DROP, usually Docker, every time it starts; published ports go through that chain. `provenza-forward.service` allows them again at boot and after each start of Docker; `provenza status` shows the check. If it fails, run `provenza units`. If Docker is not needed any more: `sudo systemctl disable --now docker.service docker.socket`. |
| The browser warns about the certificate | The DNS record does not point at the server yet, or port 80 is blocked. `journalctl -u provenza-caddy` shows the reason; Caddy retries by itself. |
| The installer says a port is in use | Another web server is running. Stop it, or see "Another web server already on 80/443" above. |
| `the database migrations failed` | `journalctl -u provenza-migrate`. After an upgrade, `upgrade.sh` has already rolled back. |
| A service stays unhealthy | `./scripts/units.sh status`, then `journalctl -u provenza-<service> -n 100`. Low memory is the usual cause: check `free -m` and the `*_MEMORY` limits. |
| `Quadlet did not generate: …` | A unit template has a key this Podman does not know. The installer prints the generator's error; `/usr/libexec/podman/quadlet -dryrun` shows it too. |
| A service fails with `start request repeated too quickly` | It crashed five times in a row; see its journal, fix the cause, then `systemctl reset-failed provenza-<service>` and start it again. |
| `network backend 'cni'` | Podman was set up with the old CNI networking. Install `netavark aardvark-dns`, set `network_backend = "netavark"` under `[network]` in `/etc/containers/containers.conf`, and run `podman system reset` (it deletes Podman's containers, images and volumes: only on a host that has no Provenza data in Podman yet). |
| `FATAL: … uses a well-known default value` | A secret in `deploy/.env` was edited to a weak value. Generate a new one with `openssl rand -base64 48`. Do not change `ENCRYPTION_KEY`: rotate it with `scripts/rotate_encryption_key.py` (see `deploy/README.md`). |
| An administrator forgot their password | Create another administrator with `create-admin` (see Operating). |
| An administrator lost their two-factor device | Another administrator: **Settings → Users → Reset 2FA**. |

## Security checklist

- [ ] `deploy/.env` is backed up off the server, and only root can read it on the server.
- [ ] Backups are copied off the server.
- [ ] Two-factor sign-in is required, at least for admins and approvers.
- [ ] SSH accepts keys only (`PasswordAuthentication no`), and the firewall allows only 22, 80 and 443.
- [ ] `ALLOW_PUBLIC_SIGNUP` is left `false`.
- [ ] You upgrade regularly: `sudo ./upgrade.sh`.

See also [SECURITY.md](../SECURITY.md) and [deploy/README.md](../deploy/README.md)
for the details of the stack.
