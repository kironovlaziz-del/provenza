# Agent signatures: how to sign, how to verify without trusting the server

Provenza records what agents delegate and do. When an agent has a signing
key, each delegation, each recorded action and each agent-to-agent message
is signed by the agent itself — with Ed25519, or, for a **hybrid** key, with
Ed25519 and the post-quantum ML-DSA-65 over the same bytes. This page specifies the format, and shows how anyone — an
auditor, a regulator, the agent's owner — can verify a record **without
trusting the Provenza server**.

## What a signature proves, and what it does not

A valid signature proves that whoever holds the private key matching the
signer's public key approved exactly these bytes. It does not tell you
*whose* key that is. The verification data (payload, signature, public key)
comes from the Provenza server, so a compromised server could, in principle,
swap all three for its own key and data.

The defence is the **key fingerprint**:

1. the agent's owner generates the key pair where the agent runs, registers
   only the public key, and writes down its fingerprint;
2. the verifier computes the fingerprint of the signer key on their own side
   (the browser, or `tools/provenza_sign.py`) and compares it with the
   owner's.

Matching fingerprints plus a valid signature mean the record was signed by
that agent's key — whatever the server says. A mismatch means the record is
not from that key.

Keys generated by the server ("quick start") are returned once and not
stored, but the server had the private key at that moment. Records signed
with such a key are marked `key_origin: "server"`; for evidence that does
not depend on the server, use agent-held keys.

## Keys

- Algorithm: **Ed25519** (RFC 8032).
- Public key: the 32 raw bytes, **standard base64** (44 characters).
- Fingerprint: `SHA256:` + base64 of SHA-256 over the 32 raw key bytes,
  without `=` padding (50 characters). It looks like an OpenSSH fingerprint
  but is not one: `ssh-keygen -l` hashes the SSH key blob and gives a
  different value.
- The key must be a canonical encoding of a point in the Ed25519
  prime-order subgroup. Small-order ("weak") keys are refused at
  registration and never treated as valid: with such a key a fixed
  signature verifies for every message.

Generate a key pair where the agent runs (add `--hybrid` for the
post-quantum scheme below):

```bash
pip install cryptography
python tools/provenza_sign.py keygen
# private_key  ...   <- stays with the agent
# public_key   ...   <- register this in Provenza
# fingerprint  SHA256:...   <- give this to the auditor
```

Register the public key when creating the agent (`public_key` in
`POST /api/v1/agents/register`, or the "agent uses its own key" option in
the UI), or later with `POST /api/v1/agents/{id}/signing-key`. Changing the
key does not break old records: each signed record stores the public key
that verified it (`signer_public_key`), and the agent's page lists every
key with the period it was current.

## Hybrid post-quantum signatures (Ed25519 + ML-DSA-65)

Ed25519, like every elliptic-curve scheme, would fall to a large quantum
computer; a record signed today can be forged then. ML-DSA (FIPS 204, the
NIST lattice-based standard) is designed to resist that, but is young. A
hybrid key uses both, and **a record is valid only if both signatures
verify** — a forger has to break both schemes.

- Scheme name: `ed25519+ml-dsa-65` (classical keys: `ed25519`).
- ML-DSA-65, *pure* mode, empty context string, over the **same canonical
  bytes** as the Ed25519 signature (no pre-hash).
- ML-DSA public key: the 1952 raw bytes, standard base64. Signature: 3309
  bytes, base64. Private key: the 32-byte FIPS 204 seed, base64.
- Fingerprint of a hybrid key: `SHA256:` + unpadded base64 of SHA-256 over
  the 32 raw Ed25519 bytes **followed by** the 1952 raw ML-DSA bytes. One
  value pins both halves; it differs from the Ed25519-only fingerprint.
- Requests carry the ML-DSA signature next to the Ed25519 one:
  `pq_signature` on `/agents/{id}/delegate`, `/agents/actions/record` and
  `/a2a/send`. For a hybrid agent, `signature` alone does not verify: a
  delegation or action is refused, and a message counts as having an
  invalid signature (rejected when the A2A guard is in enforce mode,
  flagged in monitor mode — the same as any other bad signature).

```bash
python tools/provenza_sign.py keygen --hybrid
# private_key, pq_private_key   <- stay with the agent
# public_key, pq_public_key     <- register both (public_key + pq_public_key)
# fingerprint SHA256:...        <- covers both keys

python tools/provenza_sign.py sign PRIVATE_KEY payload.json --pq-private-key PQ_SEED
# {"signature": "...", "pq_signature": "..."}
```

An organization can **require** hybrid keys (Agent identity → "Require
post-quantum signatures", `require_pq_signatures`). Then new keys and key
changes must be hybrid (`agent.pq_required`), and agents without a hybrid
key — Ed25519-only, or no signing key at all — are refused when they
delegate or record actions, and their messages are rejected in every A2A
guard mode, until they get one. Records signed
earlier keep verifying with the key that signed them.

## Canonical form

The signature is over the UTF-8 bytes of the payload in this canonical JSON
form — exactly what Python produces with

```python
json.dumps(payload, sort_keys=True, separators=(",", ":"))
```

- object keys sorted at every level (by code point);
- no whitespace;
- strings escaped as JSON, with **every character above U+007E written as
  `\uXXXX`** (lowercase hex, UTF-16 code units — characters outside the BMP
  become surrogate pairs), so the result is pure ASCII;
- numbers are integers (timestamps in Unix seconds);
- `null`, `true`, `false` as usual.

Example: the task "Отчёт ✓" is signed as `"\u041e\u0442\u0447\u0451\u0442 \u2713"`.

Verifiers should not re-serialize: Provenza returns the exact signed text as
`signed_message`. Check the signature over those bytes, then check that
`signed_message` is the canonical form of the payload you are shown.

### Delegation payload

```json
{"chain_id":<chain id or null>,"delegated_capabilities":[<sorted>],
 "expires_in":<seconds or null>,"from_agent_id":<agent id>,
 "issued_at":<unix seconds>,"nonce":"<single-use>","task":"<text>",
 "to_agent_id":<agent id>}
```

`delegated_capabilities` is sorted before signing.

### Recorded action payload

```json
{"action_type":"...","agent_id":<id>,"chain_id":<id or null>,"check_id":<id>,
 "input_sha256":"<hex>","output_sha256":"<hex>","tool_name":"..."}
```

`check_id` is the string token returned by `/actions/check`.
`input_sha256` / `output_sha256` are SHA-256 hex digests of the input and
output in the same canonical form.

## Evidence files

The delegation map offers "Download evidence"; the API serves the same JSON
at `GET /api/v1/agents/delegation-hops/{id}/verification` and
`GET /api/v1/agents/actions/{id}/verification`:

```json
{
  "format": "provenza-signature-evidence/1",
  "record": "delegation_hop",
  "record_id": 42,
  "agent_id": 7, "agent_name": "support-bot",
  "algorithm": "ed25519+ml-dsa-65",
  "signed_payload": { ... },
  "signed_message": "{\"chain_id\":null,\"delegated_capabilities\":[...],...}",
  "signature": "<base64>",
  "public_key": "<base64>",
  "pq_signature": "<base64, hybrid keys only>",
  "pq_public_key": "<base64, hybrid keys only>",
  "key_fingerprint": "SHA256:...",
  "key_origin": "agent",
  "server_verified": true
}
```

`algorithm` is `ed25519` or `ed25519+ml-dsa-65`; for a classical key the
two `pq_` fields are `null`. A verifier decides the scheme from the keys,
not from the label: if `pq_public_key` is present, the ML-DSA signature
must verify too.

`key_fingerprint`, `server_verified` and `key_origin` are the server's
statements. A verifier recomputes the first two; `key_origin` ("agent":
only the public key was ever registered, "server": generated at
registration) cannot be checked from the evidence — the fingerprint
comparison is what makes the result independent of it.

## Verifying offline

```bash
python tools/provenza_sign.py verify evidence.json --fingerprint SHA256:<from the agent's owner>
```

It checks that `signed_message` is canonical, that it matches
`signed_payload`, that the signature is valid — for a hybrid key, both
signatures — and, with `--fingerprint`, that the signer key is the expected
one. Exit status 0 means verified.

With OpenSSL 3 instead (bash; OpenSSL does not reject weak keys, so also run
`tools/provenza_sign.py fingerprint <public_key> [<pq_public_key>]` to be
sure the key is a real one and to get the fingerprint to compare):

```bash
jq -j .signed_message evidence.json > msg.bin
jq -r .signature evidence.json | base64 -d > sig.bin
# wrap the raw key in SubjectPublicKeyInfo DER (fixed 12-byte Ed25519 prefix)
( printf '\x30\x2a\x30\x05\x06\x03\x2b\x65\x70\x03\x21\x00'; jq -r .public_key evidence.json | base64 -d ) > pub.der
openssl pkeyutl -verify -pubin -inkey pub.der -keyform DER -rawin -in msg.bin -sigfile sig.bin
```

For a hybrid key, also the ML-DSA-65 half (OpenSSL 3.5 or later):

```bash
jq -r .pq_signature evidence.json | base64 -d > pqsig.bin
# SubjectPublicKeyInfo DER for ML-DSA-65: fixed 22-byte prefix + 1952-byte key
( printf '\x30\x82\x07\xb2\x30\x0b\x06\x09\x60\x86\x48\x01\x65\x03\x04\x03\x12\x03\x82\x07\xa1\x00'
  jq -r .pq_public_key evidence.json | base64 -d ) > pqpub.der
openssl pkeyutl -verify -pubin -inkey pqpub.der -keyform DER -rawin -in msg.bin -sigfile pqsig.bin
```

Both commands must print "Signature Verified Successfully".

The browser check on the delegation map does the same — Ed25519 with
WebCrypto, ML-DSA-65 with the `@noble/post-quantum` library bundled into the
app (nothing is loaded from a CDN) — shows the fingerprint it computed itself and only the content of the signed
message. It is convenient, but it runs code served by Provenza — for proof
that does not depend on the server, use the offline check.
